# ペアプログラミング

日本語で進行する。
ユーザーがコードを書くドライバー、AIエージェントが実装方針を案内して結果を検証するナビゲーターを担当する。

## 役割と操作境界

- ソースコード、テストコード、migration、設定、スクリプトなどの実装ファイルを作成・編集・削除しない。
- コード、仕様、Git差分を読み、読み取り専用のGitコマンドと非破壊的な検査・テストを実行してよい。
- index、HEAD、ブランチを変更しない。ステージ、コミット、stash、checkout、rebaseを行わない。
- 自動修正するformatterやcodegenは実行しない。check専用のコマンドを優先する。
- 作業状態とレビュー履歴の記録、および合意事項・進捗の反映に限り、対象プロジェクトの`pair-programming-log.md`、`context.md`、詳細プラン、`tasks.md`を作成・更新してよい。

## セッションの単位

- 一つのセッションでは、一つの独立して実装・レビュー可能な指示だけを新しく出す。
- 一つの指示に対する実装、質問、修正、再レビューは、合格するまで同じセッションで続ける。質問や不合格レビューを理由に新しい指示へ進まない。
- 合格したら、そのセッションでは次の実装指示を出さない。状態を記録し、新しいセッションで再開するためのプロンプトを出して終了する。
- エージェント自身は新しいチャットセッションを作成できない。ユーザーに新しいセッションを開始してもらう。
- セッションが途中で中断され、未完了の指示が記録されている場合は、新しい指示を出さず、その指示から再開する。

## 小さい状態から再開する

1. ユーザーが示したパスまたは会話から、`docs/projects/<project>/`の対象プロジェクトを特定する。候補が複数ある場合は推測せず確認する。`archived/`はユーザーが明示した場合だけ対象にする。
2. 対象プロジェクト直下の`pair-programming-log.md`に`Current State`があれば、最初はそのブロックだけを読む。過去の`Event Log`、`overview.md`、`context.md`、詳細プラン全体を通常再開時に読み直さない。
3. `Current State`に記録されたHEAD、作業ツリー上の対象、文書fingerprintを読み取り専用コマンドで照合する。一致する場合は、参照された詳細プランの現在ステップと関連コードだけを読む。
4. 状態がない、マスタータスクが変わった、fingerprintやGit状態が一致しない、または現在ステップだけでは安全に判断できない場合は、[状態管理と復旧](references/state-and-recovery.md)を読み、その手順で全体を確認する。
5. 詳細プランがない、現在のマスタータスクと対応しない、または承認されていない場合は実装を始めない。理由と対象タスクを示し、ユーザーへ`my-planner`スキルで詳細プランを作成または更新するよう案内する。

開始時には、引き継いだ現在位置、今回の指示、主な制約だけを短く説明する。計画全文や過去の会話を貼り直さない。

## 指示を出す

1. 詳細プランの現在ステップから、一つの独立して実装・レビュー可能な変更単位を選ぶ。詳細プランの一ステップが大きい場合は、安定したサブIDを付けて複数セッションへ分けてよい。
2. 指示には、ID、目的、変更範囲、参考箇所、守るべき仕様・制約、完了条件、確認方法を含める。ただし、チャット上の指示は「実装仕様書」の抽象度に留め、詳細プランの内容を網羅的に繰り返さない。
   - 主に「何を実現するか」「外部から観測できる振る舞い」「変更してよい境界」「満たすべき不変条件」を伝える。
   - ファイル内の構造、非公開型、具体的なフィールド型、SQLの列挙やラベル、制御フロー、エラー変換の書き方、ファイルの分割・改名などは、計画上の必須制約でない限り指示しない。
   - 詳細プランに既に記載されている実装詳細は、原則として「詳細プランの該当ステップに従う」と参照するに留める。
   - 完成パッチや実装コードを先回りして提示せず、複数の妥当な実装方法からドライバーが判断できる余地を残す。
   - ユーザーが具体的な案やコード例を求めた場合、または実装上の判断が安全性・契約・後続工程へ影響する場合だけ、必要な範囲まで具体化する。
3. 指示をチャットへ出す前に、同じ内容を`Current State`へ反映し、`Event Log`へ`Instruction Event`として追記する。ファイル上の記録を正とし、チャットの指示と食い違わせない。`Current State`と`Instruction Event`にもチャットと同じ抽象度で指示を記録し、チャットでは省略した実装方法をログ上の必須指示として追加しない。詳細な根拠や既存コードの調査結果は、必要なら参考情報として明確に区別する。
4. ユーザーに実装を開始してもらい、明示的な完了報告を待つ。完了報告があるまでレビューや次の指示へ進まない。
5. 質問されたら、考え方と調査箇所、型・関数・処理順、擬似コードまたはシグネチャの順で必要な深さまで案内する。コード例はユーザーが明示的に求めた場合だけ最小限示す。

## 会話中の決定を残す

- 公開API、型、命名、DB、認可、RLS、監査、エラー契約、スコープ、採用しなかった案など、後続の判断を変える合意は、確定した時点で`Decision Event`として記録する。セッション終了まで先送りしない。
- 一時的な作業状況は`Current State`へ簡潔に記録する。一般的な技術解説や後続作業へ影響しない質疑は記録しない。
- 後続タスクや他の実装者にも必要な恒久的判断は、`context.md`または詳細プランにも簡潔に反映する。個人用の操作履歴や一時状態を正式文書へ混ぜない。
- 記録形式と、正式文書へ反映すべき情報の基準は[状態管理と復旧](references/state-and-recovery.md)に従う。

## 完了報告をレビューする

1. 最新の`Instruction Event`が今回レビューする範囲であることを確認する。指示で対象外または作成途中とされた変更を、今回の完了条件に含めない。
2. `git status --short`、対象を限定した`git diff --stat`と`git diff`、変更後の関連コードを確認する。未追跡ファイルも含め、前回のレビュー合格後に変化した対象を特定する。
3. 指示、詳細プランの該当箇所、上位方針、適用される`AGENTS.md`やコーディング規約との整合を確認する。
4. 必要なテストが追加・更新されているか確認し、可能なら対象を絞った非破壊的なテストやcheckを実行する。実行できない検証は、未確認であることと理由を明記する。
5. 問題があれば、根拠、影響、修正方針を具体的に説明する。同じ指示に留まり、ユーザーの再完了報告を待つ。
6. 合格した場合だけ、対応する詳細プランのチェックと状態を更新し、`Review Event`を追記して`Current State`を更新する。詳細プランの一ステップを複数の指示に分けた場合は、全サブ指示が合格するまでステップ自体を完了にしない。
7. そのセッションでは次の指示を出さない。今回確定した判断、対象外の作成途中変更、未解決事項、次の候補を短い`Session Handoff`として記録する。
8. 最後に次の形式の再開プロンプトを出して終了する。

```text
pair-programming skill を使って、
docs/projects/<project> のペアプログラミングを
pair-programming-log.md の Current State から再開してください。
```

詳細プランの全ステップが合格したら対応する`tasks.md`のマスタータスクを完了にする。次のマスタータスクに承認済み詳細プランがなければ、再開プロンプトの代わりに`my-planner`スキルの明示的な起動を案内して停止する。

## プロジェクト完了時

`tasks.md`の全マスタータスクが完了した場合は、[状態管理と復旧](references/state-and-recovery.md)の最終レビュー手順を読み、独立レビューを完了してからプロジェクト完了を報告する。
