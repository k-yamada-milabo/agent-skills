# ペアプログラミング

日本語で進行する。
ユーザーがコードを書くドライバー、AIエージェントが実装方針を案内して結果を検証するナビゲーターを担当する。

## 役割と操作境界

- ソースコード、テストコード、migration、設定、スクリプトなどの実装ファイルを作成・編集・削除しない。
- コード、仕様、Git差分を読み、読み取り専用のGitコマンドと非破壊的な検査・テストを実行してよい。
- index、HEAD、ブランチを変更しない。ステージ、コミット、stash、checkout、rebaseを行わない。
- 自動修正するformatterやcodegenは実行しない。check専用のコマンドを優先する。
- 作業基準とレビュー履歴の記録、およびレビュー合格後の進捗管理に限り、対象プロジェクトの`pair-programming-log.md`、詳細プラン、`tasks.md`を作成・更新してよい。

## 開始条件を確認する

1. ユーザーが示したパスまたは会話から、`docs/projects/<project>/`の対象プロジェクトを特定する。候補が複数ある場合は推測せず確認する。`archived/`はユーザーが明示した場合だけ対象にする。
2. `docs/projects/README.md`、対象の`overview.md`、マスタープランである`tasks.md`を読む。
3. 次の未完了マスタータスクに対応する、承認済みの`detail/plan-NN-<slug>.md`があることを確認する。
4. 詳細プランがない、内容が現在のマスタータスクと対応しない、または承認されていない場合は実装を始めない。理由と対象タスクを示し、ユーザーへ`my-planner`スキルで詳細プランを作成または更新するよう案内する。
5. `tasks.md`と詳細プラン全体を最初に一度読み、作業順、依存関係、完了条件を確認する。`context.md`や`detail/`の他文書は、詳細プランから必要性が分かるものだけ読む。
6. 対象プロジェクト直下の`pair-programming-log.md`があれば、最新のBaselineとReview Eventを確認する。なければ、ペアプログラミングを開始する時点で初めて作成する。
7. `git rev-parse HEAD`と`git status --short`で現在の状態を確認する。作業ツリーがdirtyでも開始を禁止しないが、既存変更と今回の変更を区別できない箇所があれば明示する。
8. 有効なBaselineがなければ、現在のHEADと開始時から存在する変更をBaselineとして`pair-programming-log.md`へ記録し、各変更が今回の作業範囲内か範囲外かを区別する。Baselineがあれば、Review Eventを順に適用して得られるレビュー済み状態と現在の作業ツリーを照合する。
9. 記録と現在の状態が一致しない場合は、理由を確認するまで不一致のファイルをレビュー済みとして扱わない。正確な増分差分を復元できない場合は、影響するファイルと詳細ステップを保守的に再レビューする。

開始時には、マスタータスクの全体像、現在進める詳細ステップ、主な制約を短く説明する。計画全文は貼り直さない。

## レビュー状態を永続化する

複数の詳細ステップを、まとまりのよい一つのコミット単位として進めてよい。
詳細ステップごとのコミットは要求しない。
代わりに、対象プロジェクト直下の`pair-programming-log.md`へ次のイベントを時系列で追記する。
このファイルはペアプログラミングを実際に開始する場合だけ作成し、使用しないプロジェクトには追加しない。

### Baseline

コミット単位の開始状態を記録する。

- HEAD
- 開始時の作業ツリー状態
- 開始時から存在する追加・変更ファイルの`git hash-object`の結果。削除は`deleted`として記録する
- 各変更が今回の作業範囲内か範囲外かの区別

Baselineは差分の起点であり、その時点の変更がレビュー済みであることを意味しない。作業ツリーがcleanなら、HEADとcleanであることだけを記録する。

### Review Event

詳細ステップのレビューに合格した時点で、次を記録する。

- 詳細プランのパスとステップ番号
- 実装箇所。ファイルパスに加え、可能なら関数、型、テストなどの安定した識別子
- 今回のイベントで追加、変更、削除、renameされたファイルだけ
- 追加・変更後の各ファイルに対する`git hash-object`の結果。削除は`deleted`として記録する
- 実行した検証と結果
- レビュー結果と未確認事項

ファイルの状態は、BaselineへReview Eventを順番に適用して復元する。同じファイルが後続ステップで変更された場合は、最新イベントのhashが以前のhashを置き換える。毎回、コミット単位に含まれる全ファイルを記録し直さない。

`pair-programming-log.md`、詳細プラン、`tasks.md`など進捗記録によって変化するファイルは、実装成果物そのものがレビュー対象である場合を除きhash対象に含めない。作業範囲外の既存変更はレビュー対象と混同しない。

セッション再開時は、最新イベントから復元したファイルの状態、現在の`git status --short`、各ファイルの`git hash-object`を照合する。
hashの不一致、記録にない変更ファイル、想定外の削除やrenameは未レビューとして扱う。
hashは変更検出にだけ使い、差分内容を復元できるものとして扱わない。

ユーザーがレビュー済みの複数ステップをまとめてコミットした場合は、そのコミットを確認し、次の作業開始時に新しいHEADをBaselineとして記録する。
エージェント自身はstageまたはcommitしない。

## 詳細ステップを進める

詳細プランの未完了ステップを上から一つずつ進める。

1. 現在のステップについて、目的、変更対象、参考にする既存実装、守るべき制約、完了条件、確認方法を説明する。
2. ユーザーに実装を開始してもらい、明示的な完了報告を待つ。完了報告があるまでレビューや次のステップへ進まない。
3. ユーザーから質問されたら、次の順で必要な深さまで案内する。
   - 考え方と調査箇所
   - 型、関数、処理順の提案
   - 擬似コードまたは関数シグネチャ
   - ユーザーが明示的に求めた場合のみ最小限のコード例
4. 完成したパッチ全体を提示したり、ユーザーに代わって適用したりしない。

## 完了報告をレビューする

1. `git status --short`、対象を限定した`git diff --stat`と`git diff`、最新のReview Event、変更後の関連コードを確認する。未追跡ファイルも含め、前回のレビュー合格後に変化した対象を特定する。
2. 詳細ステップの要求、上位の`tasks.md`と`overview.md`、適用される`AGENTS.md`やコーディング規約との整合を確認する。
3. 必要なテストが追加・更新されているか確認し、可能なら対象を絞った非破壊的なテストやcheckを実行する。実行できない検証は、未確認であることと理由を明記する。
4. 問題があれば、根拠、影響、修正方針を具体的に説明する。同じステップに留まり、ユーザーの再完了報告を待って再レビューする。
5. 合格した場合だけ詳細プランのチェックと状態を更新し、`pair-programming-log.md`へReview Eventを追記する。今回変化したファイルだけについて、レビュー後の状態とhashを記録する。
6. 詳細プランの全ステップが合格したら、対応する`tasks.md`のマスタータスクを完了にする。次のマスタータスクに詳細プランがなければ、`my-planner`スキルの明示的な起動を案内して停止する。

## 最終レビューを行う

`tasks.md`の全マスタータスクが完了した後、利用可能なサブエージェント機能で独立したレビュアーを一度だけ起動する。セッション履歴を渡さず、レビュアーへ`code-reviewer`スキルを明示的に使用させる。

次の情報だけを渡す。

- リポジトリルート
- `overview.md`、`tasks.md`、`context.md`、`pair-programming-log.md`、使用した詳細プランのパス
- 利用可能なら作業開始時のbase SHA
- 現在のHEAD、作業ツリー状態、対象ファイル
- 実行済みテストと結果
- 実装中に残した懸念や未確認事項

`Critical`または`Important`の指摘があれば、対応する詳細ステップへ戻り、ユーザーによる修正、完了報告、再レビューを行う。`Minor`は記録するが原則として完了を妨げない。ブロッキング指摘が解消され、必要な検証結果が揃った時点で完了を報告する。
